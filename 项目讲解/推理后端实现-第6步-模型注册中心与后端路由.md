# 推理后端实现：第 6 步——模型注册中心与后端路由

## 目标

第 4、5 步虽然分别实现了 TensorFlow 和 TensorRT，但一个服务进程只能选择其中一个。本步骤引入 `ModelRegistry`，让同一模型同时注册多个后端，并在每个请求进入队列前完成路由：

```text
HTTP InferenceRequest
→ model 名称解析
→ backend 选择
→ ModelRegistry.resolve()
→ 任务携带选定的 IInferenceBackend
→ 工作线程执行
```

最终同一个服务进程支持：

```text
model=yolov8n, backend=auto
model=yolov8n, backend=tensorflow
model=yolov8n, backend=tensorrt
```

## JSON 模型配置

注册配置位于 `models/registry.json`：

```json
{
  "default_model": "yolov8n",
  "models": [
    {
      "name": "yolov8n",
      "version": "trt-10.0.1-fp16",
      "backend": "tensorrt",
      "path": "yolov8n_fp16.engine",
      "device_id": 0,
      "max_concurrency": 1,
      "priority": 100,
      "enabled": true
    },
    {
      "name": "yolov8n",
      "version": "tf-2.18.0",
      "backend": "tensorflow",
      "path": "yolov8n_tf218_saved_model",
      "priority": 10,
      "enabled": true
    }
  ]
}
```

相对模型路径以 `registry.json` 所在目录为基准。因此配置文件移动到其他目录时，其相对路径含义也会改变。

字段含义：

- `default_model`：请求未提供 `model` 或使用 `model=default` 时解析到的模型。
- `name`：对外模型名称，同一个名称可注册多个后端。
- `version`：写入响应的模型版本。
- `backend`：只能是 `tensorflow` 或 `tensorrt`。
- `path`：SavedModel 目录或 TensorRT Engine 文件。
- `device_id`：GPU 设备编号；TensorFlow CPU 当前不使用它。
- `max_concurrency`：为后续按模型控制并发预留；当前后端内部仍使用自己的互斥策略。
- `priority`：`backend=auto` 时选择可用项的优先级，数值越大越优先。
- `enabled`：为 false 时完全忽略该注册项。

## 配置校验

启动时检查：

- 根节点必须包含字符串 `default_model` 和数组 `models`。
- `name`、`version`、`path` 不能为空。
- 后端不能为 `auto`。
- 同一个 `(model name, backend)` 不能重复注册。
- 至少包含一个启用项。

JSON 解析继续使用项目已选定的 nlohmann/json，不引入第二套 JSON 库。

## 后端创建与初始化

`ModelRegistry` 根据编译选项创建后端：

```text
ENABLE_TENSORFLOW=ON → TensorFlowBackend
ENABLE_TENSORRT=ON   → TensorRTBackend
```

配置中存在但编译时未启用的后端会记录为不可用，不会导致配置解析失败。

初始化逐项执行：

```text
backend.load(config)
→ backend.warmup()
→ available=true
```

一个后端加载失败只禁用该注册项。只要至少还有一个后端可用，服务就可以启动；所有后端均不可用时启动失败，并汇总加载错误。

## 路由规则

### 模型解析

```text
model=default → registry.default_model
明确模型名       → 原样查找
不存在的模型     → 422 MODEL_UNAVAILABLE
```

### 显式后端

`backend=tensorflow` 和 `backend=tensorrt` 只查找指定项。该项未编译、加载失败或不存在时返回：

```text
422 BACKEND_UNAVAILABLE
```

显式后端不会回退，避免调用方指定 GPU 却意外使用 CPU。

### auto

`backend=auto` 从模型的所有可用注册项中选择 `priority` 最大者：

```text
TensorRT priority 100
TensorFlow priority 10
→ TensorRT
```

TensorRT 在启动加载或 warmup 阶段失败时会变为不可用，此时自动选择 TensorFlow。

如果 TensorRT 已加载成功，但某个请求推理失败，不会把该请求重新送到 TensorFlow。这样可以避免延迟翻倍、重复计算，以及 GPU 故障被静默掩盖。

## 调度器调整

旧调度器持有单个 Backend：

```text
InferenceScheduler → backend_
```

现在调度器持有 ModelRegistry。`submit()` 在持有队列锁时完成模型和后端解析，并把选中的 `shared_ptr<IInferenceBackend>` 放进 Task：

```text
Task {
  request,
  completion,
  backend,
  enqueuedAt
}
```

工作线程调用任务自己的 `backend->infer()`。后端选择在入队时已经确定，不会因为排队期间的其他请求而改变。

保留了旧的单 Backend 构造函数，所以无 TensorFlow/TensorRT 依赖的 MockBackend 构建和原有调度测试仍可工作。

## 启动行为

同时构建两个真实后端：

```bash
cmake -S . -B build \
  -DENABLE_TENSORFLOW=ON \
  -DENABLE_TENSORRT=ON
cmake --build build -j
```

服务器启动后读取 `models/registry.json`，加载并预热两个后端，然后才开始接受请求。

如果两个真实后端都未编译，服务器继续使用 MockBackend，不要求模型配置或外部推理依赖。

## 测试

新增 `ModelRegistryTest`，覆盖：

- 同一模型注册 TensorFlow 和 TensorRT。
- `auto` 选择高优先级 TensorRT。
- 显式 TensorFlow 严格路由。
- TensorRT 加载失败时 `auto` 回退 TensorFlow。
- 显式 TensorRT 在加载失败后不可用。
- 不存在模型无法解析。

组合配置共有 7 个测试，全部通过，包括两个真实模型后端。

同一服务进程的 HTTP 验证结果：

```text
requested auto       → backend tensorrt   → 5 detections
requested tensorflow → backend tensorflow → 5 detections
requested tensorrt   → backend tensorrt   → 5 detections
```

## 本步骤边界

- 配置只在进程启动时读取，不支持热更新。
- `max_concurrency` 已进入配置结构，但尚未形成每模型信号量。
- 所有模型共享同一个全局任务队列和工作线程池。
- 没有模型查询、健康检查或管理 API。
- 不进行运行时自动故障转移。
