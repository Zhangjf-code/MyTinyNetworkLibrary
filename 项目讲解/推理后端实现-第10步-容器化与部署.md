# 推理后端实现：第 10 步——容器化与部署

## 1. 本步目标

前面的服务已经具备推理、动态路由、健康检查和 Prometheus 指标，本步将其整理为可部署的 GPU 容器，并将原先写死在代码中的运行参数改为环境变量。

新增文件：

- `Dockerfile`：CUDA 12.4 多阶段构建。
- `compose.yaml`：单机 NVIDIA GPU 部署示例。
- `.dockerignore`：排除本地依赖、Git 数据和构建产物。

## 2. Docker 镜像结构

### 2.1 构建阶段

构建阶段使用 `nvidia/cuda:12.4.1-devel-ubuntu22.04`，安装 CMake 和 C++ 编译器，然后下载：

- TensorFlow C 2.18.0 CPU 版。
- TensorRT 10.0.1.6 for CUDA 12.4。

两个归档包都使用与 `tools/fetch_*.sh` 相同的 SHA256 校验值。校验不通过时构建立即失败，不会使用未验证的二进制库。

CMake 同时开启：

```text
ENABLE_TENSORFLOW=ON
ENABLE_TENSORRT=ON
```

### 2.2 运行阶段

运行阶段使用更小的 CUDA runtime 镜像，只复制：

- `HttpServer` 和 `libmytinymuduo.so`。
- TensorFlow 运行库。
- TensorRT 运行库。
- `models/` 模型与注册表。
- `root/` Web 静态文件。

编译器、CMake、头文件和下载缓存不会进入最终镜像。

`.dockerignore` 排除了本机 `.deps`，否则每次构建都需要向 Docker daemon 传输约 4 GB 的无用上下文。

## 3. 运行时配置

`src/http/main.cc` 支持以下环境变量：

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `MYWEBSERVER_PORT` | `10000` | HTTP 监听端口，范围 1–65535 |
| `MYWEBSERVER_INFERENCE_WORKERS` | `2` | 推理调度工作线程数 |
| `MYWEBSERVER_QUEUE_CAPACITY` | `128` | 最大排队任务数 |
| `MYWEBSERVER_MODEL_REGISTRY` | 编译时默认路径 | `registry.json` 路径 |
| `MYWEBSERVER_HTML_PATH` | 编译时默认路径 | Web 控制台首页路径 |

端口、worker 和队列容量会做严格的正整数与上限校验，非数字、零、负数或超出范围时服务会输出明确错误并以非零状态退出。

启动日志会输出生效的端口、worker 数、队列容量和注册表路径，便于确认容器环境变量是否生效。

## 4. 优雅停机

容器平台停止服务时默认发送 SIGTERM。服务启动前会在主线程屏蔽 SIGINT/SIGTERM，使后续创建的 EventLoop、推理 worker 和模型库线程继承该信号掩码。一个专用线程通过 `sigwait()` 同步等待停机信号：

```text
SIGTERM
  -> sigwait 线程
  -> EventLoop::quit()
  -> 唤醒 epoll
  -> scheduler.stop()
  -> join worker
  -> 释放模型与 CUDA/TensorRT 资源
  -> 进程以 0 退出
```

这种做法没有在 POSIX 异步信号处理器中调用 C++ IO、互斥锁或内存分配，避免不可重入操作导致死锁。

Compose 设置 `stop_grace_period: 30s`；如果有已进入后端的长时间推理，调度器会等待它结束，因此生产环境应将宽限期设置为大于最长推理时间。

## 5. 构建与启动

宿主机需要：

1. NVIDIA 驱动，`nvidia-smi` 正常。
2. Docker Engine。
3. NVIDIA Container Toolkit。
4. 支持 `gpus: all` 的 Docker Compose。

启动：

```bash
docker compose up --build -d
docker compose logs -f inference
```

验证：

```bash
curl http://127.0.0.1:10000/healthz
curl http://127.0.0.1:10000/v1/models
curl http://127.0.0.1:10000/metrics
```

停止：

```bash
docker compose down
```

Dockerfile 自带 `HEALTHCHECK`，每 15 秒请求一次 `/healthz`，启动宽限期为 30 秒，连续三次失败后容器标记为 unhealthy。

## 6. 模型与 TensorRT Engine 注意事项

`models/yolov8n_fp16.engine` 会被打包进镜像。TensorRT Engine 与 TensorRT 版本、CUDA 版本和 GPU 架构密切相关。当部署 GPU 与生成该 Engine 的机器不同时，应在目标 GPU 上使用仓库的 ONNX 和构建脚本重新生成 Engine，而不应假设现有 Engine 可跨机器通用。

如需要在不重建镜像的情况下更换模型，可在 `compose.yaml` 中增加只读挂载：

```yaml
volumes:
  - ./models:/opt/mywebserver/models:ro
```

注册表仍然只在进程启动时读取，更换后需要重启容器。

## 7. CMake 构建边界修正

原顶层 CMake 通过 `aux_source_directory(src/http)` 把 `main.cc` 同时编译进了 `libmytinymuduo.so` 和 `HttpServer` 可执行文件。当 `main.cc` 出现有析构函数的全局 C++ 对象时，动态符号互置可能造成重复析构。

本步将 `main.cc` 从共享库源文件中过滤，使共享库只包含可复用组件，进程入口只属于 `HttpServer` 可执行文件。

## 8. 验证结果与限制

已完成：

- 无 GPU 构建与 6 项测试，全部通过。
- TensorFlow + TensorRT 联合构建与 8 项测试，全部通过。
- 无效端口配置能拒绝启动并返回非零退出码。
- 自定义端口、worker 数和队列容量能正常生效。
- 真实 SIGTERM 能唤醒所有 EventLoop，停止调度器并以退出码 0 结束。

当前宿主机没有安装 Docker CLI/Engine，因此无法在本机实际执行 `docker build` 和 `docker compose config`。Dockerfile 中的基础镜像拉取、依赖下载和容器内 GPU 验证，需在已安装 Docker 与 NVIDIA Container Toolkit 的机器上完成。
